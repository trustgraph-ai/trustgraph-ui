# Candidate UX Signal Mechanisms

UX features that improve the shopping experience while producing structured interaction signals as a byproduct. Every mechanism below does something the user genuinely wants — the signal emission is a side effect of better UX, not data collection disguised as interface.

All signals map to the interaction ontology (`ix:` namespace) and would be written to the knowledge graph as triples via the `/api/v1/flow/{flow}/import/triples` WebSocket endpoint.

---

## 1. Refinement Buttons (Structured Rejection)

**What the user sees:** When product cards are displayed for a slot, a row of contextual buttons appears below the grid instead of a generic "see more" link. Each button describes *why* the shown products aren't right.

**Example for GPU slot:**
- "Too expensive" — fetch cheaper alternatives
- "Need more VRAM" — filter for higher VRAM
- "Too large for my case" — filter by GPU length
- "Lower power draw" — filter by lower TDP

**Example for CPU slot:**
- "Too expensive" — re-sort by price-asc
- "Need more cores" — filter for higher core count
- "Need less power/heat" — filter by lower TDP
- "Different brand" — exclude current brand

**Example for Case slot:**
- "Too expensive" — re-sort by price-asc
- "Too big" — filter smaller form factor
- "Too small" — filter larger form factor

**What it does for the user:** Immediately replaces the product grid with options that address their specific concern. Faster path to the right product than typing a message.

**Signals emitted per click:**

| Ontology type | Properties |
|---|---|
| `ix:ResultsViewed` | `shownProduct` links to original products |
| `ix:Objection` (for "too expensive", "wrong brand") | `hasObjectionType`, `statedReason`, `objectionResolved: false` (until they select from the refined set) |
| `ix:PrioritySignal` (for "more VRAM", "more cores", "lower power") | `priorityDimension`, `signalStrength: "strong"` |
| `ix:BudgetSignal` (for "too expensive") | `budgetConstraintType: "hard-limit"` |

**Compounding effect:** If the user hits "Too expensive" across multiple slots, the system accumulates BudgetSignal triples. The assistant could proactively suggest budget rebalancing before the user hits the same wall on every component.

**Query refinement mapping:** Each button maps to a SPARQL query adjustment (additional filters, different sort order, relaxed constraints). The replacement products directly address the stated concern.

**LLM context:** The rejection is forwarded to the prompt as structured context, e.g. `[User rejected CPU recommendations: too expensive]`, so the assistant adapts its tone and future price targeting.

## 2. Post-Selection Reason Tap

**What the user sees:** Immediately after clicking "Select" on a product card, a brief overlay appears with 4-5 quick-tap options: "Best value", "Best performance", "Brand preference", "Assistant recommended it", "Other". One tap and it disappears. Optional — can be dismissed without choosing.

**Why it works:** The user just made a decision. Their reasoning is freshest right now. It feels like a natural "confirm your choice" moment, not a survey. It takes under a second and then it's gone.

**Signals emitted:**

| Ontology type | Properties |
|---|---|
| `ix:DecisionPoint` | `selectedOption`, `rejectedOption` (the other shown products), `decisionReasoning` (the tapped reason) |
| `ix:PrioritySignal` | `priorityDimension` mapped from reason ("Best performance" → "performance", "Best value" → "price-to-performance") |
| `ix:SatisfactionSignal` (if "Assistant recommended it") | `signalStrength: "moderate"` — the user trusted and followed the advice |

**Analytics value:** Comparing stated reasons to actual product attributes reveals whether users' mental models match reality. If users select the cheaper GPU but tap "Best performance", either the UI isn't communicating specs clearly or users define performance differently than benchmarks do.

## 3. "Why This One?" Explainer Button

**What the user sees:** A small "Why?" button on each product card. Tapping it shows a brief, contextual explanation of why that product suits their specific build and use case. Generated by the LLM using the build state and user's stated priorities.

**Why it works:** Users want to understand *why* a product is recommended, not just *that* it is. This replaces the user having to type "why did you recommend the 7800X3D?" — same information, one tap instead of a typed question.

**Signals emitted:**

| Ontology type | Properties |
|---|---|
| `ix:ProductViewed` | `involvedProduct`, `dwellTimeSeconds` (time between opening and closing the explainer) |
| `ix:QuestionAsked` | `questionText: "Why this product?"`, `questionTopic` (the product name) |
| `ix:PrioritySignal` (weak) | The user is interested but uncertain — the tap indicates they're evaluating, not just browsing |

**Follow-up signals:** Whether the user selects the product after reading the explanation creates a natural `ix:AnswerReceived` with `answerSatisfying` inferred from the subsequent action. Selected → satisfying. Skipped → not convincing enough.

## 4. Soft Preference (Star/Heart) on Product Cards

**What the user sees:** A small star or heart icon on each product card. Tapping it marks the product as "liked" without adding it to the build. Liked products could be shown in a small "Saved" section for reference.

**Why it works:** Users often like a product but aren't ready to commit — maybe they want to see what else is available first, or they're waiting to see if it fits the budget once other components are chosen. This gives them a way to bookmark without deciding.

**Signals emitted:**

| Ontology type | Properties |
|---|---|
| `ix:PrioritySignal` (moderate) | The user expressed a preference without commitment |
| `ix:DecisionPoint` (when they later select a different product) | `optionConsidered` includes the starred product, `selectedOption` is the actual pick, `rejectedOption` includes the starred one — revealing the gap between preference and purchase |

**Analytics value:** The delta between "liked" and "bought" is rich signal. A product that gets starred frequently but selected rarely has a specific friction point — price, compatibility, or something else preventing conversion despite appeal.

## 5. Attribute Priority Ranking

**What the user sees:** At the start of a build (or optionally when entering each slot), a row of 3-4 draggable attribute chips appears: "Performance", "Price", "Efficiency", "Capacity" (contextual per component type). The user drags to rank what matters most.

**Why it works:** Takes 2-3 seconds. The ranking directly controls the sort order and weighting of the product query, so the user sees it as "tell us what matters and we'll show you better options." Tangible, immediate payoff.

**Signals emitted:**

| Ontology type | Properties |
|---|---|
| `ix:PrioritySignal` (one per attribute) | `priorityDimension`, `signalStrength` mapped from position (1st = "strong", 2nd = "moderate", etc.) |

**Query effect:** The ranking maps to SPARQL sort order. If the user ranks Price > Performance > Efficiency, the query sorts by price-asc with a secondary sort on performance. The products shown immediately reflect their stated priorities.

**Compounding effect:** Priority rankings from early slots inform later slots. If the user ranked Price first for CPU, the system could default to price-first sorting for GPU too, while allowing them to re-rank.

## 6. Comparison Mode

**What the user sees:** A "Compare" toggle or the ability to tap two product cards to view them side-by-side with specs aligned. Differences are highlighted. Available whenever multiple products are displayed.

**Why it works:** Users naturally compare — this just makes it structured and visual instead of forcing them to scan back and forth between cards. Reduces cognitive load during the decision.

**Signals emitted:**

| Ontology type | Properties |
|---|---|
| `ix:ComparisonViewed` | `involvedProduct` (the pair), `dwellTimeSeconds` |
| `ix:PrioritySignal` (inferred) | Which spec rows the user lingers on in comparison mode reveals what attributes they're evaluating. If they spend time on the VRAM row → `priorityDimension: "VRAM"` |
| `ix:DecisionPoint` (on subsequent selection) | The comparison pair becomes `optionConsidered`, with a richer context than a standard grid selection |

**Analytics value:** Which product *pairs* are most frequently compared reveals the user's real consideration set. Products that appear together in comparisons compete in the user's mind, even if they differ in price tier or brand.

## 7. Budget Slider with Live Feedback

**What the user sees:** Instead of (or in addition to) typing a budget number, a slider that shows real-time feedback: "At $1200: entry GPU + mid CPU" → "At $1500: mid GPU + mid CPU" → "At $1800: high-end GPU + high-end CPU." The tiers and descriptions update as the slider moves.

**Why it works:** Most users don't know what their budget *buys*. The slider gives them immediate context, helping them set a realistic budget rather than an arbitrary number. It also lets them explore "what if I spent $200 more?" without committing.

**Signals emitted:**

| Ontology type | Properties |
|---|---|
| `ix:BudgetSignal` (one per significant pause point) | `statedBudget`, `budgetConstraintType` inferred from behaviour — if they slide up to $2000 then back down to $1500, the $1500 is a "hard-limit"; if they slide up and stay, it's "flexible" |

**Analytics value:** The slider's movement pattern reveals budget psychology. Users who immediately slide to max and work down have a different mindset than users who start at their comfort point. The final resting position versus the initial typed budget shows the gap between "what I want to spend" and "what I'm willing to spend."

## Implementation Priority

Ranked by signal quality relative to implementation effort:

1. **Refinement Buttons** — highest value. Structured rejection reasons, immediate query improvement, clean signal triples. Every button press is a strong, typed signal.
2. **Post-Selection Reason Tap** — high value, low effort. One overlay, one tap, rich DecisionPoint data. Works within the existing selection flow.
3. **"Why This One?" Explainer** — moderate effort (needs LLM call per tap). Good engagement signal from the tap pattern. Improves the experience for uncertain users.
4. **Comparison Mode** — moderate effort. Natural interaction pattern, good ComparisonViewed data. Already partially supported by the `compare` action in the prompt vocabulary.
5. **Soft Preference (Star/Heart)** — low effort. Preference-vs-purchase gap is analytically interesting. Risk: if unused, it's just visual clutter.
6. **Attribute Priority Ranking** — moderate effort. Clean PrioritySignal data. Risk: adds a step before seeing products, which conflicts with the "show products fast" principle. Best as optional.
7. **Budget Slider** — higher effort (needs tier estimation logic). Rich BudgetSignal data. Could replace or complement the text-based budget input.

## Signal Transport

All signals are emitted as RDF triples via the existing bulk import WebSocket:

```
ws://<host>/api/v1/flow/{flow}/import/triples?token=...&workspace=...
```

Each message is a single triple: `{"s": "subject-uri", "p": "predicate-uri", "o": "object-value"}`

An event emission is a burst of triples sharing the same subject URI (the event instance), sent in quick succession over the WebSocket. The connection can be kept open for the duration of the session.

Event URIs follow the pattern: `http://trustgraph.ai/interaction/{session-id}/event/{sequence-index}`
Session URIs: `http://trustgraph.ai/interaction/session/{session-id}`
Journey URIs: `http://trustgraph.ai/interaction/journey/{journey-id}`
